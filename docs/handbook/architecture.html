03 · Deep Codebase Architecture

Architecture & Data Flow

From process startup in server/main.ts to real-time WebSocket frames in src/store/office.ts, here is how every module wires together without circular sprawl.

Server Boot Lifecycle (bin/arimaops.mjs → server/main.ts)

When ArimaOps launches (via CLI, pnpm dev:hq, or compose.yaml), bin/arimaops.mjs verifies Node.js ≥ 22.13 (the minimum version where node:sqlite loads without a flag), validates --repo and --port, and imports dist-server/main.mjs (or setup.mjs for arimaops setup). Inside server/main.ts, startup follows a deliberate sequence:

  1. Scrub parent agent variables first: Line 11 imports ./lib/scrubEnv before any other module. If you accidentally start HQ inside an active AI coding CLI session, scrubParentSession(process.env) strips parent session variables before sessions.ts copies process.env into TERM_ENV.
  2. Fix PTY permissions & migrate home: ensurePtyHelperExecutable() repairs node-pty spawn-helper permissions; migrateHome() ensures ~/.arima is ready.
  3. Seed built-ins & open-core seam: seedBuiltins(hqDb()) inserts the built-in templates into SQLite; loadEe() dynamically imports ee/ only if present and enables features authorized by the offline Ed25519 license.json.
  4. Load projects sequentially: Reads registered non-archived repos from SQLite + any --repo path and awaits startProject() (server/project.ts) one at a time so shared setup checks and sbx calls don't contend on start.
  5. Start Docker egress proxy & schedulers: If Docker is available, ensureNetwork() creates hq-agents (br-hq) and startEgressProxy(projects, port) listens on 172.30.0.1:8420. Then background timers start for nightly backups, pending memory extraction, daily memory digests, daily models.dev free-model refreshes, and 09:00 / 18:00 standup notes.
  6. Listen on HTTP + extra hosts: startHttp() binds 127.0.0.1:7420 plus 172.30.0.1:7420 (so container agents can reach hooks and MCP), then re-runs container reachability checks.

The Hub: Single Source of Truth (server/hub.ts)

Every loaded project owns one Hub instance holding an OfficeSnapshot in memory. Notice three subtle engineering patterns inside server/hub.ts:

  • Snapshot + Delta stream: Newly connected browsers receive the entire OfficeSnapshot once ({ type: "snapshot", snapshot }), followed only by tiny incremental OfficeEvent objects (task.updated, agent.updated, message, terminal.output).
  • Overlay state without clobbering truth (holdForAccess / workState): If a container agent tries to reach an unapproved domain, HQ marks its UI status "needs-input" (glowing amber) so you see it immediately. Meanwhile, hub.held remembers what the agent was actually doing underneath ("working" or "idle") so Inbox delivery checks hub.workState() and restores the real state the moment you click Allow or Deny.
  • Streaming secret redaction on terminal output: hub.terminal(agentId, data) never sends raw PTY bytes straight to the WebSocket. It passes chunks through redactor().stream() (server/credentials/redact.ts), which even buffers partial trailing prefixes up to 80 ms so a vault key split across two TCP packets cannot leak to a viewer!

Storage Architecture & Crash-Safe SQLite

ArimaOps separates machine-wide relational data from per-project runtime files and git-committed project definitions. Every SQLite database opens via openDb() (server/lib/docs.ts) with file mode 0600, PRAGMA journal_mode = WAL, and busy_timeout = 5000.

Figure 3.2 · Three-Tier Storage Layout & Ownership SQLite WAL + Git
Why one shared ~/.arima/arima.db for typed tables? Cross-project dashboards (Grid view), account-level spend caps, and transactional GDPR-style forgetProject() deletes (DELETE ... WHERE project_id = ?) all run cleanly in one place.

Crash-safe migration (server/lib/docs.ts): Originally, ArimaOps wrote plain JSON files. When migrating to SQLite, readDoc(file) / writeDoc(file) kept the exact file-path interface so callers barely changed: on first access, adopt() imports an existing JSON file inside a transaction and renames it to <file>.pre-sqlite.bak. Tested in scripts/docs-test.ts by firing SIGKILL mid-write across 5 rounds—the database always preserves a whole valid snapshot.

Command Boundary & Open-Core Seam (ee/)

  • Command parity & ownerIf: Every WebSocket command in server/commandPolicy.ts declares a minimum role (viewer, operator, owner), optional stepUp: true, Zod tuple schema, and an optional ownerIf(args, ctx) hook. Example: an operator may restart a sandboxed agent, but sendTerminalInput or updateAgent automatically escalates to owner-only if that agent runs in local mode (because a local terminal is a shell on the host machine!).
  • Open-core boundary (server/features.ts & server/license.ts): Core code never statically imports ee/. At startup, loadEe() checks if dist-server/ee.mjs (or ee/index.ts) exists, dynamically imports its exported features map, and starts only the features explicitly listed in an Ed25519-signed ~/.arima/license.json verified offline against the embedded public key.

Frontend Architecture (src/)

The React 19 UI cleanly decouples rendering from transport through the OfficeDataSource interface (src/data/source.ts):

  • Live vs Demo behind one interface: When a browser has a token or hq-live session, src/store/office.ts instantiates createWsSource(). When opened with plain Vite (or ?mock=1), it instantiates createMockSource()—letting you develop and test every screen at http://localhost:5178/?mock=1 with zero server running.
  • Responsive shell split at 1000 px: src/App.tsx measures window.matchMedia("(min-width: 1000px)"). Wide screens render Deck.tsx (DeckHeader, DeckRail, ParticleCore, AgentOrbit, HomePanels, StageRibbon, and right SlideOver panels). Narrow screens render CompactApp.tsx (bottom tab navigation + full-screen drawers).
  • Theme & type discipline: src/ui/theme/projectTheme.ts computes data-theme (build, redteam, blueteam, purpleteam) and sets it on <html>, driving CSS variables (--accent, --accent-2, --accent-glow) across every component without per-component domain booleans. Typography strictly uses sizes 12 / 13 / 15 / 20 / 28 px and weights 400 / 500 / 600. Modals/slide-overs (SlideOver.tsx, TaskSheet.tsx) render via createPortal(..., document.body) so page transition contexts never clip them underneath the header.
