Ops, Ubuntu Desktop Icon & Tablet Integration

Exact commands to control the running Docker HQ server, the complete root-cause diagnosis of why the Ubuntu desktop icon fails when Docker HQ is live, how Tablet/Android integration works, and all five security boundaries.

1. Starting, Stopping & Inspecting ArimaOps

In production on your machine, ArimaOps runs as a Docker Compose service (compose.yaml → container arimaops-hq-1) with network_mode: host and restart: unless-stopped. That is why it comes back automatically across reboots and holds ports 127.0.0.1:7420, 172.30.0.1:7420, and 172.30.0.1:8420.

~/projects/arimaops — Control Live Docker HQ & Dev Modes
# Stop the running HQ server cleanly (keeps ~/.arima data & stays off across reboots)
docker compose stop hq

# Stop AND remove the container (still preserves ~/.arima data)
docker compose down

# Start it again (or rebuild after editing server/ or src/)
docker compose up -d hq
docker compose build hq && docker compose up -d hq

# Inspect live HQ logs or an agent's tmux screen inside the container
docker logs -f arimaops-hq-1
docker exec arimaops-hq-1 tmux ls
docker exec arimaops-hq-1 tmux capture-pane -p -t hq-<project>-<agent> -S -40

# Local bare-metal dev (stop Docker HQ first because both want port 7420)
pnpm dev:hq

# Safe UI-only mock mode (runs alongside Docker HQ with zero interference)
HQ_PORT=59999 pnpm exec vite --port 5178 --strictPort
# Open http://localhost:5178/?mock=1

2. Ubuntu Desktop Icon: Why Clicking It Breaks

The desktop shortcuts ~/Desktop/arimaops.desktop and ~/Desktop/arimaops-remote.desktop (installed by scripts/launcher/install-desktop.sh) are valid and GNOME-trusted, and both call ~/.local/bin/arimaops-launch (copied from scripts/launcher/arimaops-launch.sh). Clicking the icon behaves erratically for three concrete bugs inside arimaops-launch.sh that predate Docker Compose and the SQLite migration:

Bug in arimaops-launch.shWhat the Script DoesWhat Actually Happens
1. Ignores Docker HQ (lines 49–60)Only checks if a bare-metal PID file exists at ~/.arima/logs/server.pid.When arimaops-hq-1 is running in Docker, there is no server.pid file. The launcher assumes HQ is off and tries to start a second bare-metal Node process.
2. Port & SQLite collision (lines 63–68)Tries port 7420 (or bumps to 7421 if busy) and launches node bin/arimaops.mjs.Docker HQ already owns 127.0.0.1:7420 and the egress proxy 172.30.0.1:8420. The bare-metal spawn either crashes with EADDRINUSE (logged in ~/.arima/logs/server.log) or spins up a conflicting second server sharing ~/.arima/arima.db.
3. Reads deleted projects.json (lines 18–24)Parses ~/.arima/projects.json to build the recent-projects Zenity picker.docs.ts migrated projects.json into ~/.arima/arima.db and renamed the file to projects.json.pre-sqlite.bak. So the recent list is always empty and it drops straight to a raw folder browser.
Learn by Fixing It in Lab 1

The clean fix is to check http://127.0.0.1:7420/api/health (or docker ps) before spawning anything, read recent projects straight from ~/.arima/arima.db with Node's built-in node:sqlite, and open the browser directly to the running server. You'll build and test this exact fix in Lab 1.

3. Tablet & Phone ("Tab") Integration

ArimaOps supports tablets and phones without duplicating frontend logic. Four pieces work together:

  1. One responsive React app: useDesktopHud() in src/App.tsx watches matchMedia("(min-width: 1000px)"). Landscape tablets (≥ 1000 px) get the full Command Deck (Deck.tsx); portrait tablets and phones (< 1000 px) switch smoothly to CompactApp.tsx (bottom tabs: Home, Board, Inbox, Agents, Chat, More, with drawers opening full-screen).
  2. Tailscale + device cookie + 24h TOTP step-up: Running HQ with --remote (and serving via Tailscale HTTPS) issues a 30-day hq_sid cookie stored in SQLite. Any risky remote action (terminal typing, secrets, settings, approvals) triggers remote.stepup until you enter a 6-digit authenticator code (valid 24 hours per device).
  3. Native Android WebView + WebMessagePort bridge: android/app/src/main/java/com/arimaops/app/MainActivity.java opens connect.html on first launch, validates HTTPS (or localhost) via ServerUrl.java, and creates a dedicated WebMessageChannel sent only to the verified main-frame origin. JavaScript receives frozen window.ArimaNative (platform(), switchServer(), pushToken()) in src/lib/native.ts, and Android's Back button delegates to window.__arimaBack() to close open drawers cleanly before navigating back.
  4. FCM Push + Deep Links: After login, useNativePush() sends the Firebase token to POST /api/push/register. PushDevices.watch(hub) (server/push.ts) watches Hub events and sends high-priority FCM data alerts. Tapping a notification fires arimaops://open?project=…&open=… into MainActivity, and useDeepLink() in App.tsx opens that exact agent, finding, board, or Inbox item.

Security detail: PushService.java drops incoming pushes for any server origin not in the user's saved list, and PushDevices.notify() re-checks live authorization right before calling FCM so revoking a user or changing them to viewer stops operator alerts immediately.
