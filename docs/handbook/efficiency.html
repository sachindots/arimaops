How Efficient, How Fast, How Best

Why ArimaOps uses the specific patterns it does—how it cuts token burn, RAM footprint, and latency while keeping a strict engineering bar enforced by automated invariant tests.

1. Token & Dollar Cost Efficiency

Multi-agent orchestrators easily burn through quotas by dumping entire codebases, chat histories, and bloated tool lists into every prompt. ArimaOps attacks token waste from six angles:

MechanismWhere in CodeHow It Saves Tokens & Money
Bounded ~4k-token briefsserver/brief.tsbuildBrief() builds one structured brief capped to BRIEF_BUDGET. If over budget, it deterministically sheds oldest handoffs → oldest ledger items → half of memory → older facts → spec → description, telling the agent what was omitted so it can pull deeper via recall() only if needed.
Lean mode resetserver/adapters.ts (CLEAR_COMMAND)Clears the CLI conversation between tasks so task #5 doesn't carry stale diff context from task #1. Only the structured brief and handoff carry forward.
3-line message disciplinesrc/data/messageTags.ts, server/mcp.tssend_message nudges agents when replies exceed 3 short lines and starts messages with crisp tags (Done:, Blocked:, Question:, FYI:), stripping greetings and sign-offs via tidy().
Role-scoped MCP toolsserver/mcp.tsWorkers never receive Lead-only tool schemas in their MCP context, and non-security projects never load finding schemas—shrinking input tokens and preventing wrong tool calls.
Tiered paid + free model routingsrc/data/teamSetup.ts, server/freeModels.tsproposeSetup() puts paid models (Opus/Sonnet) on the Lead and coding seats, while assigning light/review/QA roles to rotating zero-cost models from 4 sources (OpenCode Zen, OpenRouter :free, NVIDIA NIM, AMD Token Lab).
Spend caps + Overflowserver/spendCaps.ts, server/overflow.tsPolls API-key spend every 30s (default $5/day, $50/month; 80% alert, 100% auto-pause of workers). When a paid subscription hits a limit, overflow.ts offers an ask-first move to the role's fallback or best free model.

2. RAM & Compute Efficiency

Running 5–8 AI CLIs and sandboxes on a developer laptop or an 8 GB EC2 instance fails quickly if every project spawns its own server, database, and half-RAM VMs:

  • Single Node process across all projects: One HQ server hosts every active repo, sharing one HTTP/WS server, one SQLite connection pool, one egress proxy, and one free-model catalog cache.
  • On-demand workers with 2-minute grace (server/onDemand.ts): Only the Lead stays running when a project is idle. Workers start automatically when assigned an unblocked task and shut down GRACE_MS = 120_000 ms after their last open task completes (reusing the session if another task arrives quickly).
  • Tamed sandbox RAM + 3 GB host headroom (server/accounts.ts): Docker Sandboxes' own default claims half of host RAM per VM! ArimaOps overrides creation with SANDBOX_DEFAULT = { cpus: 2, memoryGb: 2 } and runs fitsInRam() before starting any agent—reserving RESERVED_MB = 3072 (3 GB) for your OS, browser, and HQ, counting 500 MB per local/container agent or real reported GB per sandbox, and queuing excess on-demand starts cleanly instead of OOM-crashing your laptop.
  • Zero extra DB daemons: Replacing Neo4j (768 MB+ JVM heap/cache) with SQLite FTS5 inside ~/.arima/arima.db dropped memory-store RAM overhead to near zero while keeping full-text search and 2-hop graph traversal.

3. Speed & Latency

  • GitHub App webhooks + smart polling (server/githubApp.ts, githubSync.ts): Rather than hammering gh every second or waiting minutes, signed webhooks over Tailscale Funnel (:8443) act as instant hints that trigger an immediate PR fetch, while GhPolling falls back smoothly (20s normal, 5m safety net when webhooks are healthy). Merged PR files/checks are fetched once and cached.
  • Stacked PRs (Planner.stackBase): Dependent tasks whose parent PR is already open in review don't sit idle waiting for merge—they branch directly on top of the parent branch and rebase cleanly once the parent lands.
  • Stream-JSON vs screen scraping: In Stream-JSON mode, streamEngine.ts receives exact tool events over HTTP as Claude emits them and dispatches the next message on result with zero terminal quiet-wait timers.
  • Lean UI transport & rendering: Static assets are gzip-compressed on the fly by server/http.ts (saving ~4× bandwidth on mobile Wi-Fi) with immutable cache headers for hashed chunks, incremental WebSocket deltas avoid re-sending snapshots, and desktop page switches fade in 150 ms opacity-only.

4. Code Quality & "How Best" Engineering Practices

What separates a maintainable codebase from an AI-generated tangle is enforceable invariants. Look at how ArimaOps keeps itself clean as it grows:

Pure Logic Separated from I/O

Complex rules—server/gates.ts (11 gate evaluators), server/accounts.ts (fitsInRam), server/scorers.ts (RULES), and server/skillScan.ts—take plain inputs and return plain values with zero network or DB side effects. That lets unit tests run in milliseconds without mocks.

Automated Architecture Invariants

scripts/architecture-invariants-test.ts runs on every pnpm test and fails CI if: (1) commandPolicy.ts and commands.ts drift out of 1-to-1 parity, (2) a worker leaks a Lead-only MCP tool in any of the 9 templates, (3) Gemini/agy rule writers emit duplicate instructions, or (4) any server/*.ts file exceeds its line cap (http.ts ≤ 650, planner.ts ≤ 760, others ≤ 850).

53 Standalone Test Suites

Each subsystem has its own fast, readable scripts/*-test.ts harness executed in isolated Node processes by scripts/run-tests.mjs—including real SIGKILL crash tests for SQLite (docs-test.ts), signed GitHub webhook fixtures, and TOTP replay checks.

Factory Metrics & Task Scoring

ArimaOps measures its own agent output: server/metrics.ts computes cost per merged PR, cycle time (task_events), rework (failed gates), stalls, and owner interventions; server/scorers.ts grades finished tasks with free deterministic checks plus metered Haiku rubric checks; server/suite.ts replays tasks across models to compare cost vs quality.

5. Honest Tradeoffs & Known Limits (Senior Engineer Read)

Every architecture trades something off. Before extending or scaling ArimaOps, know where the sharp edges are today:

  • Single-machine vertical ceiling: One Node process + local SQLite WAL + host RAM fits solo developers and small teams brilliantly, with zero ops overhead. It is not designed to horizontally shard one project across multiple worker servers.
  • Container DNS is unfiltered: The :8420 allowlist proxy blocks disallowed HTTP/HTTPS connections by hostname, and DOCKER-USER drops direct outbound IP packets—but DNS queries themselves aren't filtered by the proxy yet (documented in docs/how-it-works.md).
  • Line ceilings are tight in core files: server/sessions.ts (~848 / 850 lines) and server/planner.ts (~759 / 760 lines) sit right at their invariant limits. When adding features, extract a focused pure helper module (just like server/stalls.ts and server/resumeAgents.ts) instead of cramming more logic into those files.
  • Container GitHub pushes need GH_TOKEN: Containers deliberately do not mount your host SSH keys or host gh keyring; builder seats in Container mode need a fine-grained GH_TOKEN added via App Variables to push branches.
  • Free-tier rate limits & rotation: Free model catalogs rotate daily and impose strict RPM/daily caps (OpenRouter ~50/day without top-up, NIM ~40 RPM, Token Lab ~20 RPM). Subscription plans (e.g., Claude Pro 5h windows) share limits across every seat on that account across projects.
