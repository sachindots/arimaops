Pipewell: one brief in,
a tested pipeline out

The owner wrote a one-page brief for a small data-engineering project: pull hourly weather for five cities from a free API, land it in DuckDB, build daily tables with SQL, check every table, and publish a report. An ArimaOps Dev team did the rest. Nobody on the team was a person.

What they built

Five stages, each its own command

Review

Three bugs that would have shipped

The reviewer didn't read diffs and nod. It ran each branch's tests with the earlier work merged in, tried the cases the spec cared about, and sent back what broke. The authors fixed each one with a test, and the reviewer checked again.

extract · PR #2

A partly covered day was saved empty

When the API didn't return all 24 hours for a day, the day landed as an empty file and was never fetched again. Now a day is written only when it's complete.

check · PR #5

A missing table crashed the checks

The check stage died with a traceback and wrote no results. Now a check that can't run is recorded as failed and the run exits 1.

check · PR #5

A fresh clone had nowhere to write

With no data folder yet, the database couldn't open. Now the folder is created first, with a test for a fresh clone.
